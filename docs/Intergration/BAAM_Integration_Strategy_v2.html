01 核心架構決策
已拍板架構
雙軌並行：n8n self-hosted（非醫療）+ AWS Lambda（醫療），共用同一套下游 Gmail API 發送邏輯。觸發模式統一為 event-triggered，不做 batch pull。
相同觸發邏輯，不同執行層，分界線由商家 compliance_tier 決定。
商家預約系統 / POS │ ├── 非醫療商家 ──→ n8n (self-hosted, AWS) ──→ Supabase ──→ Gmail API ──→ 客人 email │ ↕ Anthropic API │ (AI 負評判斷 / 月報生成) │ └── 醫療商家 ─────→ AWS Lambda ──→ BAAM server ──→ Gmail API ──→ 客人 email
為什麼是 event-triggered，不是 batch pull

服務完成後 1–2 小時觸發（peak gratitude moment），是 review response rate 最高的時間窗口。Batch pull 等同於隔天才發，效果遠低於即時觸發。

為什麼連預約系統，不連支付系統

支付系統只記錄「錢」，不記錄客人 email 和服務完成狀態。預約系統記錄「服務」，有完整客人資料。餐廳等純收款場景因 email 採集結構性缺失，第一階段暫不納入。

03 工具選型：三工具比較
Zapier 不選
線性 trigger→action，no-code 優先，按 task 計費。
  • ✓ SMB 品牌認知度最高
  • ✓ 上手最快
  • ✕ 按 task 計費，量大成本高
  • ✕ 條件分支、loop 能力弱
  • ✕ 無 code node，AI 整合受限
  • ✕ 商家不接觸界面，品牌優勢無效
Make 曾考慮
視覺化 scenario，月費制，有原生預約系統 connector。
  • ✓ 原生支持 Vagaro / Mindbody / Acuity
  • ✓ 月費制，比 Zapier 便宜
  • ✓ 視覺化流程，分支 / loop 支持
  • ✕ 封閉平台，無 code node
  • ✕ AI agent 能力弱，AI 整合需繞路
  • ✕ 數據過 Make 雲端，數據主權弱
  • ✕ 量大後仍有費用壓力
n8n 選擇
Self-hosted，開源，原生 AI Agent node，直連 Supabase。
  • ✓ Self-hosted = 零 per-execution 費用
  • ✓ 原生 AI Agent node（接 Anthropic API）
  • ✓ 直連 Supabase，去重邏輯無中間層
  • ✓ Code node：判斷邏輯精確可控
  • ✓ 數據留在 BAAM AWS infra，HIPAA 邊界乾淨
  • ✓ $180M C 輪 / $2.5B 估值，平台持續投資
  • ✕ 需 JT 建 Docker infra（半天工作量）

選 n8n 的核心理由

BAAM Full Service 的三個差異化功能——AI 負評判斷、24 小時自動回覆、每日異常監控——都需要 AI Agent node 和直連資料庫的能力。Make 和 Zapier 做不到。n8n 是唯一能在同一個平台承載「發送自動化」和「AI 判斷」兩層邏輯的工具，不需要中途切換平台。

05 n8n 完整架構

三條 workflow 分階段建置，線一先跑驗證穩定，再加線三，最後接線二 AI Agent。點擊各條線展開詳細步驟。

觸發層
預約系統 webhook → n8n Webhook node
邏輯層
Wait 1.5h → Supabase 去重查詢 → AI Agent node
執行層
Gmail API 發送 → Supabase 寫入記錄
1
Review Request 發送
P1 — 先建 展開 ▸
Webhook node
接收預約系統 appointment.completed 事件。觸發條件必須是 completed，不是 booked（客人可能 no-show）。
Wait node
Delay 1.5 小時。服務完成後立刻發感覺像機器人，1.5 小時後發更像店主親自寄。
Supabase node
去重查詢：此 email 在過去 30 天內是否有 sent 記錄？是 → Stop。否 → 繼續。去重在 n8n 直連 Supabase 完成，無 HTTP 中間層。
Supabase node
寫入 review_request 記錄，status: queued。
HTTP node
呼叫 Gmail API 發送 review request。寄件人：商家自己的 Gmail（OAuth），sender reputation 屬於商家本人，不混入 shared IP pool。
Supabase node
更新 status: sent，記錄 sent_at timestamp，供去重和報表使用。
2
負評 AI 判斷與回覆（Full Service）
P3 — 線一穩定後建 展開 ▸
Schedule node
每小時掃描一次 GBP 新評論。
HTTP node
抓取商家 Google Business Profile 評論 API，過濾出未回覆的評論。
IF node
評分 ≤ 3 星？是 → 負評流程。否 → 好評回覆（同樣進 AI node 生成感謝回覆）。
AI Agent node
接 Anthropic API。System prompt 包含商家口吻設定 + 回覆策略框架。判斷評論類型：常規情緒投訴 → 直接生成回覆；涉及具體事實 / 補償要求 → 生成草稿 + flag 升級。
IF node
需要升級確認？否 → 直接發布到 GBP（80% 常規情況，24 小時 SLA）。是 → 發通知給商家（email / webhook），等待確認後發布（20% 複雜情況，48 小時 SLA）。
Supabase node
記錄回覆記錄，供月報統計使用。
注意：回覆內容不得包含虛假陳述，策略為「承認、道歉、提出解決方案」。
3
每日績效監控 + 月報
P2 — 線一後建 展開 ▸
Schedule node
每天 08:00 執行。遍歷所有 active 商家。
Code node
彙整昨日數據：發送數、開信率、新評論數、spam rate（投訴數 / 發送數）、競爭對手評論均值（GBP API）。
IF node（異常偵測）
三個異常條件：① Spam rate > 0.1% → 暫停該商家發送 + 告警 Owen；② 3 天內 3 條以下 3 星 → flag 惡意刷評，協助商家向 Google 提交申訴；③ 評分下降 > 0.2 → 通知商家。
Supabase node
寫入每日 snapshot，供月報使用。
AI Agent node（每月 1 日）
彙整當月數據，生成自然語言月報：評分趨勢、同業對比、下月建議。以商家 email 發出。月報是 retention 工具，讓商家每月看到成果，替續費做決策。
建置順序

線一（發送）先跑，驗證穩定後加線三（監控），最後接線二（AI 回覆）。JT 不需要一次建完。三條線共用同一個 n8n instance 和 Supabase。

06 商家 Onboarding SOP

Step 1 — 商家分類確認（E / Ava）

  • 確認行業，填入 CRM compliance_tier（standard / hipaa）
    E
  • 灰色地帶標記 pending review，不自動歸軌
    E
  • HIPAA 商家通知 Owen 走 Lambda 路線
    E

Step 2 — 預約系統確認（E 問商家）

  • 問：「你現在用什麼預約系統？」確認平台類型
    E
  • 無預約系統 → 確認 Stripe checkout 有無開啟 collect email
    E
  • 純現金商家 → 退回 Self-serve Path A
    E

Step 3 — API Access 取得（商家操作，E 提供 Scribe 截圖教學）

  • 發送對應平台的 access 設定截圖教學
    E → 商家
  • 商家將 API key / OAuth token 填入 BAAM onboarding 表單
    商家
  • 確認 Gmail OAuth 已連接（發送用）
    E 確認

Step 4 — n8n Workflow 建置（Owen / JT）

  • 依平台選擇對應 workflow 模板，填入商家憑證
    Owen
  • 設定 Wait node（1.5 小時）
    Owen
  • 確認 Supabase 去重 query 正常
    Owen

Step 5 — 測試（不可跳過）

  • 建一筆 test appointment，標記 completed
    Owen
  • 確認 n8n webhook 收到觸發
    Owen
  • 確認去重邏輯正常（同 email 第二次不發）
    Owen
  • 確認 Gmail 發出測試信，內容和連結正確
    Owen
  • 商家本人確認收到，顯示名稱無誤
    商家確認

Step 6 — 開啟 Live Mode

  • 測試全過，Owen 啟用 n8n workflow active 狀態
    Owen
  • CRM 標記 onboarding status → active
    E
  • 發送商家確認信：自動化已啟動
    E
07 合規要求
合規項目適用範圍BAAM 責任商家責任
CASL（加拿大）所有加拿大商家服務條款明確說明確保客人有 express / implied consent
CAN-SPAM（美國）所有美國商家提供 unsubscribe 機制確認客人有真實交易記錄
HIPAA美國醫療 covered entityAWS Lambda + BAA，不走 n8n簽署 BAAM BAA 補充協議
Gmail API ToS所有商家OAuth 只申請 gmail.send scope；Google Cloud project 需完成 OAuth verification授權 BAAM 使用其 Gmail 帳號
負評回覆內容Full Service 商家回覆策略為「承認、道歉、解決方案」，禁止虛假陳述複雜情況需確認後發布
Google 申訴（惡意刷評）Full Service 商家代辦申訴流程，協助整理材料理解成功率由 Google 判定，BAAM 不保證移除
執行前阻塞性問題

Google Cloud OAuth verification 狀態：未驗證 app 授權頁顯示警告，商家看到會流失。需 JT 確認。｜負責人：JT｜建議截止：本週內
